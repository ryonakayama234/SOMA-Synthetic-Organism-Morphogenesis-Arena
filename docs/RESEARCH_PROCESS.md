# 一つの能力・機能を研究する手順

~~~mermaid
flowchart TD
  A["GitHub Issue\n一つの問いと完成条件"] --> B["仕様ノート\n仮説・反証・観測量"]
  B --> C["専用ブランチで最小実装"]
  C --> D["テスト／反復実験"]
  D --> E["生ログ・図・差分を記録"]
  E --> F["PRでレビュー"]
  F --> G{"採否判断"}
  G -->|改善| B
  G -->|採用| H["mainに統合\nIssueを完了"]
  G -->|未解決| I["保留理由を残す"]
~~~

## Issue（課題）の約束
一つのIssueにつき、一つの主要能力。「セルが動く」と「合体する」を同時に実装しない。事前に成功・失敗の指標を定める。

## 仕様ノートに必ず記載する項目
1. 問い：何が不明か
2. 仮説：どの条件なら何が起きると予測するか
3. 代替仮説・失敗条件：どうすれば反証できるか
4. 操作変数／統制変数
5. 観測量と単位
6. 技術的な入力と出力（図を併記）
7. テスト／受入基準
8. 実験で見られたこと：未実施なら未実施と明記
9. 関連Issue・参考文献

## 判定を四つに分ける
- **支持**：今回の条件では予測と整合。ただし一般的に正しいとは限らない。
- **反証**：観測と予測が矛盾した。
- **不明**：計測や統制が不足。
- **未実施**：まだデータがない。

## 開発・記録の役割
- **研究者（ユーザー）**：面白さ、方向、重要な研究判断を評価。
- **実装担当（AI）**：Issue、ブランチ、コード、テスト、資料更新。
- **監査役（別視点のAIまたは独立レビュー）**：設定漏れ、仮説への後付け、計測不備、再現性を点検。
- Git操作は実装担当が代行する。main を変更する前に新規の大きな主張・破壊的変更がないかレビューする。

## 記録とコンテキスト
- コードだけでなく、なぜ採用したかを仕様ノートまたは意思決定記録へ書く。
- 失敗結果は残す。研究結果を完成した事実のように書き換えない。
- 資料を追加するときは README と関連資料からリンクする。
- 将来のAIは [AGENTS.md](../AGENTS.md) → README → 対象仕様 → Issueの順に読む。

## 変更と同時に更新する「研究コンテキスト一式」（2026-10-14追加）

機能ごとのPRは**コードだけで完了としない**。原則として次の資料を同じPRで整合させる（該当しない場合は理由を書く）。

- topics/Fxxx/SPEC.md：問い、仮説、対立仮説、設計仮定、測定量と単位、受入・反証条件、未解決事項。
- docs/ARCHITECTURE.md：今回の能力が既存部品のどこに挿入されるかをMermaid図で可視化し、「概念／実装済み」を区別する。
- docs/DATA_CONTRACTS.md：設定→真の状態→観測／イベント→ログ／成果物の構造と流れをMermaid図で可視化する。
- experiments/Fxxx/PLAN.md：対照条件、固定条件、測定量、再現方法。実行後は生ログ・図をActions artifact等に保管し、findings/Fxxx-validation.mdに支持／反証／不明の判定を記録。
- README.md：入口・進捗・関連PR/Issueのリンク。必要ならAGENTS.mdと文献図書館も更新。

仕様だけのPRでは「proposed・未実施」を明記し、実測のない数値を成果として扱わない。**正式採用は独立レビュー、対照実験、記録整合の確認後にのみ行う**。保留PRのコードを別機能が暗黙に使うことを禁止する。
