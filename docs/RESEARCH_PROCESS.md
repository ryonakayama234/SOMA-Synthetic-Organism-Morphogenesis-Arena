# 一つの能力・機能を研究する手順

~~~mermaid
flowchart TD
  A["GitHub Issue\n一つの問いと完成条件"] --> B["仕様ノート\n仮説・反証・観測量"]
  B --> C["専用ブランチで最小実装"]
  C --> D["テスト／反復実験"]
  D --> E["生ログ・図・差分を記録"]
  E --> F["PRでレビュー"]
  F --> G{"採否判断"}
  G -->|改善| B
  G -->|採用| H["mainに統合\nIssueを完了"]
  G -->|未解決| I["保留理由を残す"]
~~~

## 問いの選定は研究アジェンダで行う

実験の実行前に、[研究憲章](PROJECT.md) → [研究アジェンダ](RESEARCH_AGENDA.md) → **研究対象Issue / SPEC / PLAN** の順で、長期目的と候補選定の理由を確認する。アジェンダは優先する**未解明の因果関係**と判断基準を扱い、個体に望ましい成果を直接報酬として与える指令でも、凍結済みFxxx実験の事後変更権限でもない。候補を選んだら、この文書の従来どおりの事前登録・監査・科学的採否へ進む。

## Issue（課題）の約束
一つのIssueにつき、一つの主要能力。「セルが動く」と「合体する」を同時に実装しない。事前に成功・失敗の指標を定める。

## 仕様ノートに必ず記載する項目
1. 問い：何が不明か
2. 仮説：どの条件なら何が起きると予測するか
3. 代替仮説・失敗条件：どうすれば反証できるか
4. 操作変数／統制変数
5. 観測量と単位
6. 技術的な入力と出力（図を併記）
7. テスト／受入基準
8. 実験で見られたこと：未実施なら未実施と明記
9. 関連Issue・参考文献

## 判定を四つに分ける
- **支持**：今回の条件では予測と整合。ただし一般的に正しいとは限らない。
- **反証**：観測と予測が矛盾した。
- **不明**：計測や統制が不足。
- **未実施**：まだデータがない。

## 開発・記録の役割
- **研究者（ユーザー）**：面白さ、方向、重要な研究判断を評価。
- **実装担当（AI）**：Issue、ブランチ、コード、テスト、資料更新。
- **監査役（別視点のAIまたは独立レビュー）**：設定漏れ、仮説への後付け、計測不備、再現性を点検。
- Git操作は実装担当が代行する。main を変更する前に新規の大きな主張・破壊的変更がないかレビューする。

## 記録とコンテキスト
- コードだけでなく、なぜ採用したかを仕様ノートまたは意思決定記録へ書く。
- 失敗結果は残す。研究結果を完成した事実のように書き換えない。
- 資料を追加するときは README と関連資料からリンクする。
- 将来のAIは [AGENTS.md](../AGENTS.md) → README → 対象仕様 → Issueの順に読む。

## 機能の完成条件：コード・図・構造・実験を同一PRで更新（2026-10-13追加）

単一機能Fxxxを完成したと判定するPRには、以下の**5点を同じレビュー単位**として揃える。新機能だけを先にmainへマージして資料を後追いにしない。

1. **コード／テスト**：`soma/`・`tests/`・`experiments/` の必要最小範囲。隣の能力を先取りしない。
2. **システム図**：`docs/ARCHITECTURE.md` の図に現在のデータや制御の実際の接続、未実装の点線、責務境界を表示。
3. **データ構造**：`docs/DATA_CONTRACTS.md` に設定、状態、時系列ログ、単位、版、キー、入力検証を記録。
4. **実験記録**：`findings/Fxxx-validation.md` に観測値・不確実性・再現条件・反証や限界を残す。未実施は未実施と記載。
5. **現在地**：`README.md` の状態・資料リンクと対象の `topics/Fxxx-.../SPEC.md` を更新。

PRレビューでは「コードが動くか」に加え、「図が現在の実装を表すか」「データ契約と実ログが一致するか」「仮説を実験で検証したか」を独立のチェック項目にする。仕様提案だけのPRは、これらを**未実装と明記**するなら先に作成してよいが、実験に成功したとは扱わない。

## 個人研究向けレビュー・限定採用手順（2026-10-23）

外部の第三者・大学の査読者が確保できない場合も、**研究用ソフトウェアの限定採用は妨げない**。既存の「別視点のAIまたは独立レビュー」という監査役の定義に従い、以下を明確に区別する。役割を切り替えた同一AIの点検や同じ研究工程内で実装した独立検証器は、**外部の独立した査読ではない**。

1. 観測より前に問い、seed、比較対象、解析単位、棄却条件を事前登録・凍結し、SHAを残す。実験後に望ましい結果が出るよう変更しない。
2. 実装と別経路の検証器で**保存済み生データ**から再計算し、改竄後に再ハッシュしたデータを拒否する。Python複数版、既存回帰、二回のバイト一致再生、正確な最終ソースSHAのCIを確認する。
3. AIが批判役を担うときは、技術的反例、負の実験結果、観測の依存性、外生情報漏洩、モデルと現実の差を記録する。**AI自己査読を独立第三者レビューと呼ばない**。
4. **限定的な測定器の採用**と、**科学的現象の支持／反証／不明／未検証**を分ける。良い結果が出ない場合も、事前固定した計測器の技術的採用は可能。
5. 技術的な未達条件は外部査読の有無と無関係に統合を停止する。満たした場合に限り、内部の限定判断をIssue/PR/findingsへ記録してmainへ統合し、統合後のCIを確認する。実世界の生物的・物理的な一般化には、追加の研究と可能なら外部レビューを求める。

これは個人リポジトリの透明性・再現性のための運用規則であり、学術的な外部査読済みという意味ではない。既存Fxxxの凍結実験条件を変更しない。
